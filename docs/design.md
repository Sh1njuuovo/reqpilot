## 1. 项目概述

需求全流程 AI 处理 Agent：把自然语言需求自动转化为需求文档（PRD）、高保真交互原型、质量审核结果与研发任务，覆盖"需求 → 设计 → 质量管控 → 研发对接"完整链路。方向取舍上选择"需求工程 Agent"档位：闭环完整、可实现可验证；"需求到代码"作为后续扩展能力，避免陷入可靠性难以证明的套壳代码生成。

### 系统主链路（四层）

1. **输入层**：自然语言需求；支持从会议纪要、聊天记录、文字批注中提取需求与变更意见。
2. **需求设计层**：LLM 生成结构化 PRD；生成高保真原型图（HTML 页面，支持基础交互）。
3. **质量管控层**：自动标注需求模糊点，覆盖交互/逻辑/权限/数据四类；以"产品经理 + 前端 + 后端 + 测试"多角色视角审核，找问题后直接给方案。
4. **研发对接层**：自动拆分任务并导出；对接 AI 研发团队；成熟场景可直接生成前端页面。

## 2. 输入与输出

输入：自然语言、会议纪要、聊天记录、历史 PRD、领域术语与规则文档、对初版方案的修改意见。

输出：结构化 PRD、需求模糊点与缺失项清单、前端/后端/测试任务列表、页面信息架构、HTML 交互原型、需求版本差异、可导入任务平台的任务数据。

## 3. 核心工作流

```text
原始需求
  → 需求解析与信息抽取
  → 领域知识检索（RAG）
  → 多角色需求审查（产品/前端/后端/测试）
  → 问题去重、分级与合并
  → 生成结构化 PRD
  → 生成 HTML 交互原型
  → 拆分研发任务并导出
```

### 3.1 需求解析

抽取项目背景、目标用户、用户故事、功能需求、规则约束、权限要求、数据字段、异常流程、验收标准。通过 JSON Schema / Pydantic 约束输出结构，解决自由生成导致的字段缺失与格式不稳定问题。

### 3.2 领域知识增强（RAG）

将领域术语、历史需求、系统说明、规则文档写入知识库；生成前检索相关知识并注入上下文，减少无效模糊点。每条规则记录来源文档与段落，实现引用追踪，降低规则幻觉风险。检索后端可插拔：本地默认为零依赖关键词后端，可选向量后端；生产环境可换 pgvector。

### 3.3 多角色审查

使用状态机编排四个审查角色：产品 Agent（目标/流程/验收标准）、前端 Agent（页面状态/交互/错误提示）、后端 Agent（接口/数据模型/权限/幂等性）、测试 Agent（边界条件/异常路径/可测试性）。审查结果统一进入问题池，执行相似问题去重、严重程度分级、证据来源记录。

### 3.4 PRD 与原型生成

PRD 采用"结构化数据 → 模板渲染"：先产出稳定的需求 JSON，再渲染 Markdown / 网页版本。原型模块根据页面描述生成单 HTML 多页面原型，支持多状态、基础跳转、表单校验、深浅色主题、PC/移动端适配。

### 3.5 人工审核与版本迭代

用户可提交修改意见，系统将反馈转为结构化变更（JSON Patch 风格：operation/target/reason/old_value/new_value），保留完整版本历史并展示受影响页面、接口与测试用例。MVP 以人工确认节点 + 全量版本快照实现。

### 3.6 研发任务拆分

从最终 PRD 生成前端、后端、数据库、测试任务，包含任务依赖关系、验收标准、工作量等级；支持 Markdown / CSV / JSON 导出，后续通过 MCP 或平台 API 写入任务系统。

## 4. 关键技术点

1. LLM 核心引擎：PRD 生成、原型代码生成、模糊点识别、需求变更整合、任务拆分。
2. MCP 协议打通外部系统：提交任务到代码平台、对接 AI 研发团队。
3. 单 HTML 多页面原型：同一 HTML 生成所有原型页面并展示基础交互，支持多状态页面与自定义样式。
4. 领域 RAG 与术语库：向量检索 + 来源引用，减少无效模糊点。
5. 结构化输出：JSON Schema / Pydantic 约束模型输出，保证字段完整与格式稳定。
6. 需求版本管理：用户反馈转成结构化变更，避免整份重新生成，保留可回溯差异。
7. 提示词变体评测：把评审提示词写成命名变体，用同一套 golden 样例做对比，按明确规则选优并留档。

## 5. 系统架构

### 分层职责

- Agent 编排层：需求解析 → PRD 生成 → 原型生成 → 质量审核 → 任务拆分的 LangGraph 工作流编排。
- LLM 接入层：模型 API + 提示词工程 + 领域知识注入。
- MCP 服务层：封装外部能力（任务系统等）。
- 原型渲染层：HTML + 单文件多页面渲染。
- 交付与迭代层：变更管理、任务同步、效果度量。

## 6. 技术难点与工程亮点

1. 长文本需求的结构化生成：分段解析 + 字段级合并 + Schema 校验，控制输出稳定性。
2. 领域知识检索：术语召回 + 向量检索 + 来源引用，减少规则幻觉。
3. 多 Agent 协同：状态机控制角色执行、并行审查、去重、汇总与人工审核节点。
4. 结构化变更与版本快照：避免整份重新生成，保留可回溯差异。
5. 质量评估体系：带人工标注的需求样例集，量化评测完整性、问题召回与一致性。
6. 安全边界：生成任务默认人工确认；外部平台写入使用白名单与审批节点。

## 7. Agent 循环设计（`src/reqpilot/agent/`）

固定管线的每个节点做什么是提前定好的，模型只在节点内部做一次生成。这条路径可预测、好评测，但回答不了"模型自己决定下一步做什么"。Agent 循环补的就是这一段。

### 7.1 循环结构

一个目标从进入循环到结束经过四件事：观察工作区、决定调用哪些工具、把工具结果写回上下文、判断是否收尾。收尾有两种情况，模型主动声明完成，或者步数预算用尽。

每轮结束后程序都会独立跑一次验收。验收通过但模型还没声明完成时，循环会提示模型调用 `goal_complete`，这样"什么时候结束"既不完全由模型决定，也不会因为模型忘记声明而白跑。

### 7.2 执行边界

`WorkspaceSandbox` 是唯一的路径入口，所有相对路径和绝对路径都会解析成真实路径再做归属判断，越界直接抛 `SandboxViolation`。命令执行只允许白名单里的只读命令，并且不经过 shell，因此管道、重定向、命令串联都不成立；`find` 的 `-exec` 系列参数和 `sort -o` 单独列为禁用参数，因为它们能把只读命令变成写操作或执行入口。

### 7.3 工具集

只保留 `ls`、`read`、`write`、`append`、`edit`、`grep`、`find`、`bash` 加一个 `remember`。取舍的理由是通用性：这类原语能覆盖工作区里的绝大多数动作，而不需要为每个功能写一个专用函数。写操作只有 write、append、edit 三个入口，便于审计工作区到底被谁改过。

`append` 是实测之后补上的。模型写一份长文档时会把它塞进一次 write 的参数里，撞上单步输出上限后参数 JSON 不闭合，调用直接失败。允许分批追加之后，长文档可以拆成几次写，配合循环里对 `finish_reason` 为 length 的识别，这条路径才稳定下来。

### 7.4 上下文与记忆

工具输出会无限增长，所以上下文有 token 预算。估算方式是中文按字计、西文按四字符一个 token 计，只用于触发阈值。超过预算的九成时，较早的消息折叠成一条摘要，并保证不把助手消息和它产生的工具结果拆开。完整记录追加在 `session.jsonl`，需要跨运行保留的结论写进 `MEMORY.md` 并在下一轮开始时注入。

### 7.5 完成判定

模型的完成声明不构成证据。`reqpilot.agent.checks` 里的校验函数直接读工作区文件：`issues.json` 是否可读、`review-fixes.md` 是否覆盖了所有 critical 与 major 问题、`tasks.md` 是否仍然存在。校验通过才把目标状态写成 completed，模型调用失败写成 failed，两种情况都进 `AgentRun` 的 trace。

步数用尽时再跑一次验收。如果工作区其实已经满足目标，只是模型没主动声明，就按 completed 记录，同时在 checks 与 fallbacks 里写明"模型未主动声明"，而不是判成 step_limit 失败。目标达成与否由验收决定，声明只是触发条件，这一点在实现里是分开的。

### 7.6 与固定管线的分工

固定管线负责产出可评测的交付物，Agent 循环负责在交付物上继续做需要自己找路的工作，比如按评审意见做整改。两者共用同一个 provider 与 trace 模型，所以一次运行的证据格式是一致的。确定性替身 provider 让循环可以完全离线测试，工具调用、验收失败回灌、步数上限这些路径都有断言覆盖。

### 7.7 提示词变体与选优

评审提示词写在 `src/reqpilot/prompt_variants.py` 里，每个变体是一个命名常量，运行期通过 `REQPILOT_PROMPT_VARIANT` 切换。`src/reqpilot/tuning.py` 用同一套 12 条样例逐变体跑一遍评测，再按固定规则选优：先过滤掉最终问题数超过预算的变体，因为收敛护栏存在的意义就是列表要能被人读完；在满足预算的变体里取问题召回最高的，并列时取列表更短的，再并列取精确率更高的。没有变体满足预算时报告会写明原因并退化为按召回选择。

选优规则写在文档和报告里，而不是留在调参人的经验里，这样换模型或扩样例集之后可以重跑同一套比较。

## 8. 生产化备注

- 知识库可替换为 PostgreSQL + pgvector，检索接口不变。
- 运行状态可持久化到 PostgreSQL；原型验证与端到端截图可接 Playwright。
- MCP server（stdio）提供 `analyze_requirement` 与 `export_tasks` 两个工具，作为外部系统接入入口。
- Agent 循环的沙箱可换成容器或远端执行环境，工具协议与验收函数不需要改动。
- 上下文压缩目前用确定性摘要，接入模型摘要只需替换 `ContextManager` 的 summarizer。
- 提示词变体可扩展到解析与 PRD 生成环节，选优规则与报告格式直接复用。
