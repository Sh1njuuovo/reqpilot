# ReqPilot 项目由来与讲述方式

这份文档解决一个具体问题：一个没有实习经历、没有企业业务背景的人，怎么把这个项目讲得既真实又站得住。

## 一句话定位

ReqPilot 是一个我做需求自查用的 LLM Agent。它把一段自然语言需求变成结构化的 PRD、产品/前端/后端/测试四个视角的评审意见、一个可点击的 HTML 原型和一份研发任务，并且在评审之后还能进入沙箱里的目标循环，把阻塞问题逐条处理掉。

## 真实动机

不要编造公司立项、团队协作或者线上用户。学生身份能接触到的真实刺激足够用了，下面三条任选一条作为主说法。

1. **课程与小组项目里的需求返工**。几个人做课程设计时，需求通常是一段话，写完就开工，做到一半才发现权限没定义、失败路径没写、验收标准只有一句"功能正常"。返工的成本最后都落在写代码的人头上。
2. **自己做兴趣项目时的自我评审缺失**。一个人写需求没有人评审，写完 PRD 也没人挑问题，很容易把"我以为的"当成"写清楚的"。
3. **读到业界公开的 PRD 与评审清单之后的迁移**。公开的产品文档模板里，评审检查项本身就是一份清单，清单可以交给模型执行，但前提是模型的输出要被结构化约束，而且要有办法衡量它找出来的问题对不对。

推荐主说法用第一条，因为它是真的会发生、也容易被追问细节的事情。第二条可以作为补充，用来说明为什么要把评审做成自动化。

## 为什么选需求工程而不是直接生成代码

这是最容易被追问的点，答案要提前准备好。生成代码的效果很难在没有真实仓库和真实测试的情况下证明，而需求质量可以用一份人工写出来的标准答案去比对。换句话说，选择需求工程是为了让这个项目有可验证的评测，而不是为了显得简单。

## 口播稿

**30 秒版**

> 这是一个做需求自查的 Agent。输入一段口语化的需求，它会先抽成结构化数据，再让产品、前端、后端、测试四个角色分别找问题，最后生成 PRD、原型和任务清单。做完之后还能进入一个沙箱里的目标循环，把评审里的阻塞问题逐条处理掉，处理没处理完由程序校验，不是模型说了算。项目的重点在评测和可靠性上，有 12 个人工标注的样例和一套可以重跑的指标。

**90 秒版**

> 起因是课程和小组项目里的需求返工。大家把需求写成一段话就开工，做到一半才发现权限、异常路径、验收标准都没写清楚，最后返工的是写代码的人。我判断这类问题有清单性质，适合交给模型做，但直接让模型输出会不稳定，所以整个项目是围绕"怎么让它稳定、可衡量"来设计的。
>
> 管线部分是固定的：需求解析、领域知识检索、四角色并行评审、去重和严重度收敛、生成 PRD、生成单文件 HTML 原型、拆分任务。模型只负责理解和生成，每一步都要求返回通过 Pydantic 校验的 JSON，校验不过给它一次修复机会，网络抖动退避重试三次，一直失败就把这次运行标成失败而不是塞一份假内容。
>
> 后面我补了一个真正的 Agent 循环。它在一个被限制住的目录里工作，只能用 read、write、edit、grep、find 和只读 bash 这几个通用工具，消息超过 token 预算就把旧消息压缩成摘要，长期结论写进 MEMORY.md。目标完成这件事不采信模型的声明，模型调用 goal_complete 只是触发一次程序侧校验，工作区不满足条件就继续跑，跑满步数预算就判定失败。
>
> 评测用的是 12 条我自己按人工评审视角写的样例。DeepSeek 实测管线成功率 12/12，问题召回率 93.8%，平均每个案例 14.1 秒。同时我把模型过度标注这件事量化了出来，粗粒度标签下的问题精确率只有 22.7%，这正好是去重和每角色 Top-5 收敛存在的理由。提示词也不是我手动试出来的，评审提示词按命名变体存放，用同一套样例逐个跑评测，再按固定规则选优，实测三个变体里 baseline 召回 90.0% 胜出，报告留档可复查。

## 能撑住追问的证据

| 追问 | 回答用哪块证据 |
| --- | --- |
| 你怎么保证模型输出稳定 | Pydantic schema 校验加一次修复、退避重试三次、失败标 failed 不产出伪结果 |
| 这算 Agent 还是固定工作流 | 固定管线之外还有目标循环，模型自己选工具、自己决定何时收尾，终止条件由程序校验 |
| 工具执行安全怎么做的 | 工作区沙箱统一解析路径，越界直接报错；bash 只允许只读白名单且不经 shell 执行 |
| 上下文会不会爆 | 有 token 预算，超过阈值把旧消息压成摘要，完整记录写 session.jsonl，长期记忆写 MEMORY.md |
| 模型自己说完成就完了吗 | 不是，goal_complete 只触发校验，校验读的是工作区文件 |
| 评测口径是什么 | 12 条人工评审视角样例，指标是字段完整性、问题召回、去重率，命令可重跑 |
| 为什么精确率只有 22.7% 还写出来 | 因为这是模型的过度标注现象，量化它是收敛护栏的设计依据 |
| 提示词怎么调的，有没有记录 | 评审提示词拆成命名变体，同一套样例逐个评测，按"先过滤超预算、再取召回最高"的规则选优，报告落盘可复查 |

## 不要说的话

- 不要说成某家公司立项、团队协作或线上运行，这些一追问就穿。
- 不要给没跑过的数字，`uv run reqpilot eval` 能重跑出来的才写。
- 不要说"用 LangChain 做的"，这个项目用的是 LangGraph 编排加自己写的 Agent 循环，用词要准。
- 不要把开源教程的项目成果当成自己的原创，被认出一次比少一个项目亏得多。

## 如果被问为什么不做更常见的项目

可以直说取舍：常见的后台管理系统或爬虫项目很难在没有真实业务的情况下写出有说服力的评测，而需求评审这件事的正确答案是可以人工写出来的，所以它更适合用来证明"我知道怎么衡量一个 LLM 应用的好坏"。
