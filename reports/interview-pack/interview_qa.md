# ReqPilot 面试官拷问 Q&A

## 一、项目定位

### 1. 介绍一下这个项目

ReqPilot 是我自己做的需求工程 Agent。输入一段口语化的需求，它会抽成结构化数据，跑产品、前端、后端、测试四个角色的并行审查，再生成 PRD、单文件 HTML 原型和任务清单。后半段是一个沙箱里的目标循环，可以在交付物上继续做需要自己找路的工作，比如按评审意见逐条整改。整个项目的重点是可靠性和可衡量，不是把功能堆出来。

### 2. 你为什么做需求评审这个方向

起因是课程和小组项目里的需求返工。需求写成一段话就开工，做到一半才发现权限、失败路径、验收标准都没定义。这类问题有清单性质，适合交给模型执行，但前提是输出要被结构化约束，而且要有办法判断它找出来的问题对不对。

### 3. 你没有实习，怎么想到做这个

学生身份能接触到的真实场景就是课程项目、小组作业和自己的兴趣项目，需求返工在这些场景里一样会发生。我没有编造业务背景，这个项目的动机、设计取舍和评测方式都能对得上代码，见 `docs/project-story.md`。

### 4. 项目为什么匹配 Agent 相关 HC

它同时覆盖了编排、工具调用、可靠性和可验证四件事。编排是 LangGraph 状态机，工具调用是沙箱里的目标循环，可靠性是结构化输出加重试加失败标记，可验证是 12 条人工标注样例加可重跑的指标。

### 5. 输入输出是什么，入口在哪

输入是自然语言需求文本，可以带领域和来源类型。输出是 ParsedRequirement、多角色审查问题列表、PRDDocument、单文件 HTML 原型、DevelopmentTask 列表，以及 AgentRun 追踪。入口有四个，CLI（smoke / demo / agent / serve / eval / tune）、FastAPI 的 POST /requirements、MCP stdio server，以及 pytest。

## 二、管线与可靠性

### 6. LangGraph 图怎么设计的，为什么用它

链路是 parse、retrieve、fan_out_review、四个并行的 review_one、merge_reviews、build_prd、build_prototype、split_tasks、finalize。parse 失败走条件边直接到 finalize 标 failed。选它是因为状态显式、有并行原语、支持人工确认中断，而且每一步都能 trace。

### 7. 四角色并行怎么实现的，踩过什么坑

用 Send 做 fan-out，路由写在 add_conditional_edges 里返回 Send 列表。坑是 LangGraph 1.x 不允许普通节点直接返回 Send 列表，第一次实现抛了 InvalidUpdateError，读源码后改成条件边才通过。四个 review_one 的结果用 reducer 合并，统一在 merge 节点去重。

### 8. 四个角色怎么避免各说各话

每个角色有职责边界，产品看目标用户和验收，前端看页面状态和校验，后端看接口、数据、权限、幂等，测试看边界和可测试性。提示词要求合并同类、每角色最多五条、宁缺毋滥，输出统一走 Pydantic schema，后处理再做跨角色去重和按严重度收敛。

### 9. LLM 输出不合 schema 或者调用失败怎么办

三层容错。校验失败给一次基于错误信息的修复机会，网络类错误指数退避重试三次，仍然失败就记 typed error 并把 run 标成 failed。原则是不产出伪结果，宁可失败也不拿假内容顶替。

### 10. RAG 怎么做的，为什么有两个后端

KnowledgeRetriever 协议统一返回带 doc_id 和 section 的 chunk，注入解析与 PRD 生成上下文，同时写进 AgentRun 的 citations 做引用追踪。默认是零依赖的关键词后端，带中文分词和术语别名扩展，另有一个基于 sentence-transformers 的向量后端，生产可以换 pgvector，接口不变。

### 11. 问题去重和收敛怎么做

先按类别加规范化标题合并跨角色同质问题，保留最高严重度并合并角色证据，再按严重度每个角色保留 Top-5，阈值由 REQPILOT_MAX_ISSUES_PER_ROLE 控制，最后重新编号。

## 三、Agent 循环

### 12. 这个项目算 Agent 还是固定工作流

两条路径都有，而且分工明确。固定管线负责产出可评测的交付物，模型在每个节点内部只做一次生成，可预测也好衡量。沙箱里的目标循环负责需要自己找路的活，模型自己选工具、自己决定什么时候收尾。回答这类问题不要只讲管线，重点讲循环的存在理由。

### 13. 循环怎么运转

每一轮做四件事，观察工作区、决定调用哪些工具、把结果写回上下文、判断是否收尾。收尾有两种情况，模型主动声明完成或者步数预算用尽。每轮结束后程序都会独立跑一次验收，如果验收已经通过但模型还没声明，循环会提示它调用 goal_complete，避免因为忘记声明而白跑。

### 14. 模型说完成了就信吗

不信。goal_complete 只是一个触发器，真正判定的是 `reqpilot.agent.checks` 里的校验函数，它直接读工作区文件。以默认的整改目标为例，校验会检查 issues.json 是否可读、review-fixes.md 是否覆盖了所有 critical 和 major 问题、tasks.md 是否还在。校验不通过会把原因回灌给模型让它继续，步数用尽则判定为 step_limit。

### 15. 工具执行的安全边界在哪里

只有 WorkspaceSandbox 一个路径入口，相对路径和绝对路径都先解析成真实路径再判断归属，越界直接抛 SandboxViolation。命令执行只允许只读白名单，并且不经过 shell，所以管道、重定向、命令串联都不成立。find 的 -exec 系列和 sort 的 -o 单独列为禁用参数，因为它们能把只读命令变成写操作或执行入口。测试里对 `cat /etc/passwd`、`find . -exec rm {} ;`、`sort -o` 这些都做了断言。

### 16. 为什么只留这几个工具

工具集是 ls、read、write、edit、grep、find、bash 加一个 remember。取舍理由是通用性，这些原语能覆盖工作区里的绝大多数动作，不需要为每个功能写一个专用函数。写操作只留两个入口，便于审计工作区被谁改过。

### 17. 上下文会不会爆

有 token 预算，默认 6000。估算方式是中文按字计、西文按四字符一个 token，只用于触发阈值。超过预算九成时较早的消息折叠成一条摘要，并且保证不把助手消息和它产生的工具结果拆开。完整记录追加到 session.jsonl，需要跨运行保留的结论写进 MEMORY.md 并在下一轮开始注入。摘要函数挂了会退到确定性摘要，压缩本身不会让循环失败。

### 18. 循环怎么测试，没有 key 也能测吗

可以。脚本化 provider 替身按固定顺序回放决策，所以工具调用、验收失败回灌、步数上限、工具越界、工具失败继续跑这些路径都能离线断言。LLM provider 那一侧用打桩的 HTTP 响应测了工具调用解析、参数坏掉时的降级、瞬时错误重试和持续失败抛错。

### 19. 拿真模型跑的时候踩过什么坑

踩了三个，都是真跑才暴露的。

第一个是上下文压缩把目标本身压掉了。第一版只把系统提示钉住不压缩，目标写在后面普通消息里，连续压缩两次之后目标被折进层层嵌套的摘要里，模型失去了目标，八步全在 ls 和 read 上打转。修法是把目标写进系统提示，同时给上下文加了钉住条数，前两条永不压缩，并补了一个连续压缩后目标和系统提示仍原样保留的测试。

第二个是工具参数被输出长度截断。模型想把 4000 多字的整改文件塞进一次 write 的参数里，撞上 max_tokens 上限，参数 JSON 没闭合，解析出来是一段原始字符串，工具报的错还是"path 必须是非空字符串"，模型看不懂就一直重试。修法是三件事，把单步输出上限提上去并做成可配置、识别 finish_reason 为 length 的截断并明确告诉模型上次调用没执行、增加 append 工具让长文件分批写。

第三个是完成判定太依赖模型的声明。有一次模型已经把文件写好了，程序侧四项验收全过，但它没在八步内调用 goal_complete，结果被判成 step_limit 失败。这个判定是错的，因为目标是否达成应该由验收决定，声明只是触发。改成步数用尽时也跑一次验收，通过就按完成记录，同时在 trace 里写明"模型未主动声明"，不掩盖这个区别。

## 四、评测

### 20. 评测指标怎么算

12 条样例各自带必须抽到的字段组和预期问题标签，标签按人工评审视角写。字段完整性是命中字段组的比例，问题召回是检出与标注的交集除以标注，去重率看跨角色合并和裁剪掉了多少条。

### 21. 精确率只有 22.7% 为什么还敢写

因为这是模型的过度标注现象，粗粒度标签下命中率被大量额外问题稀释。量化它本身就是评测设计的一部分，先量化再治理，收敛护栏就是为它存在的。给提示词加"只报有原文依据的"之后精确率会上去，但召回会掉，变体评测里能直接看到这个取舍。

### 22. 实测数字是多少

DeepSeek-chat 实测管线成功率 12/12，问题召回 93.8%，去重加裁剪减少 8.9%，平均每个案例 14.1 秒，这段是网络延迟不是本地计算。字段完整度 91.7% 是因为 case-011 是一条只有背景没有功能点的样例，按设计就是 0%。命令是 `uv run reqpilot eval`，报告落在 reports/eval。数字每次跑会有波动，有一次评测里某条用例的评审调用偶发失败，那次被我按 failed 记下来重跑，没有拿假内容顶替。

### 23. 怎么证明不是套壳

模型是唯一执行引擎，所有输出过 Pydantic schema。每次运行有输入哈希、指纹、步骤 trace 和引用。评测一键重跑 12 条样例的全部指标。测试用确定性替身锁行为，不依赖网络。失败路径有 typed error 追踪。

### 24. 提示词你怎么优化的，还是靠手调

靠手调的问题是没有记录，换个模型或者扩了样例集就说不清当初为什么这么写。所以我把评审提示词拆成命名变体放在 `src/reqpilot/prompt_variants.py`，用同一套 12 条样例逐个跑评测，再按固定规则选优。规则是两步，先过滤掉最终问题数超过预算的变体，因为收敛护栏存在的意义就是列表要能被人读完；在满足预算的变体里取问题召回最高的，并列时取列表更短的，再并列取精确率更高的。报告落在 reports/tuning，换模型后重跑同一套比较即可。

实测结果是 baseline 召回 90.0% 胜出，evidence_first 召回 85.1%，coverage_first 召回 89.7% 且精确率最高到 26.7%，但成功率掉到 75%，所以按规则还是选 baseline。

### 25. 选优规则会不会把好变体误杀

会，所以规则里留了退路。如果所有变体都超预算，报告会写明原因并退化为按召回最高选择，不会静默给出一个看起来正常的结果。选优规则本身也写在报告和设计文档里，方便质疑和调整。

## 五、工程与部署

### 26. 成本与延迟怎么考虑

模型只负责理解和生成，temperature 0.2，单次修复，三次退避重试，超时 60 秒。生产可以加输入哈希缓存、并发控制、按角色批处理。Agent 循环有步数预算，最坏情况下的调用次数是上界可控的。

### 27. 线上部署会怎么做

知识库换 pgvector，运行状态持久化到 PostgreSQL，写操作引入 Redis 和 Celery 异步，原型用 Playwright 截图验证，trace 接 Langfuse 或 OpenTelemetry，任务导出走 MCP 白名单工具并保留人工确认节点。沙箱可以换成容器或远端执行环境，工具协议和验收函数不用改。

### 28. 为什么状态先用内存加 JSON 快照

一期目标是本地可跑、可演示、可复现，数据库会抬高部署门槛。AgentRun 的全量 JSON 快照已经满足审计和回放。生产演进路径写在 docs/design.md 里，主动讲取舍比被追问时支吾好。

### 29. 最大的限制是什么，下一步

三个。领域泛化依赖知识库质量；评测规模小，12 条而且标注是我自己写的；需求版本差异和需求到代码还没做。下一步先扩样例集，加 LLM-as-judge 的问题有效性抽样，再把上下文压缩从确定性摘要换成模型摘要。

### 30. 简历里的数字怎么复现

评测数字用 `uv run reqpilot eval`，报告在 reports/eval/eval_llm_keyword_latest.md；测试数字用 `uv run pytest --cov=reqpilot`，当前是 116 个用例、93% 行覆盖率；Agent 循环的行为用 `uv run pytest tests/test_agent_loop.py tests/test_agent_sandbox.py`；提示词变体对比用 `uv run reqpilot tune`。

### 31. 如果给你一个月把它做成产品，优先级怎么排

先补需求版本差异和人工确认，interrupt 节点已经留好了；再接 MCP 写回任务平台和 Playwright 截图验证；最后做知识库治理和更大规模的评测。原则是先保证人审得住，再谈自动化程度。
